# 001 — 대규모 행사 투입 전 검토

> 2026-09-17 · 지난 주말 행사(사진 11,000장 / 작가 5명 / 참가자 300명)를 your-moment에
> 올리기 전에, AWS 비용과 서버 부하를 점검하다가 나온 것들.
> 출발은 "비용 얼마 나오나?" 였는데, 비용은 문제가 아니었고 다른 게 나왔다.

## 전제

- 사진 11,000장 — 작가 4명 × 2,000장 + 1명 3,000장
- 참가자 300명
- 원본 JPEG 5MB 가정 (10MB면 저장·전송 2배)

## 1. 비용 — 결론적으로 문제 아님

| Rekognition 인덱싱 (11,000장 × $0.001) | $11 일회성 |
| 검색 + 재매칭 | $1~8 (재매칭 구조에 따라) |

| S3 저장 (57GB) | 월 $1.4 |

선택지를 전부 버릴 수 있었다.

## 2. ⚠️ MaxFaces 두 개 — 최우선

이번 검토에서 나온 것 중 **사진 검색 품질에 직접 영향을 주는 유일한 항목.**

| 위치 | 현재 | 문제 | 소급 |
|---|---|---|---|
| `rekognition.ts:38` `IndexFaces` | 5 | 단체사진에서 **카메라에 가까운 5명만** 인덱싱. 뒷줄은 영원히 검색 안 됨 | ❌ **업로드 전 필수** |
| `rekognition.ts:60` `SearchFacesByImage` | 100 | 100장에서 잘림. 참가자 평균 등장 추정 180회 | ✅ 언제든 |

근거:
- AWS SDK 타입 문서 확인 — IndexFaces는 얼굴을 **바운딩 박스 크기순(카메라에 가까운 순)**
  으로 정렬하고 초과분을 품질 낮은 순으로 버린다. 20명 단체샷이면 앞 5명만 남는다.
- 11,000장 × 얼굴 5개 = 최대 55,000 얼굴 / 300명 ≈ 1인당 평균 180회 등장.
  상위 노출자뿐 아니라 **평균적인 참가자도 100을 넘길 가능성이 높다.**

비용 영향:
- **검색 MaxFaces 상향 = 비용 증가 0.** Rekognition은 호출당 과금이라
  결과를 몇 개 돌려주든 $0.001. 지금은 이미 계산된 결과를 버리고 있는 셈.
- 인덱싱 MaxFaces 상향 = 인덱싱 비용 변화 없음(장당 과금), 저장료만
  월 1천 원 안쪽 증가.
- `FaceMatchThreshold: 80`은 그대로. MaxFaces는 신뢰도 높은 순으로 자르므로
  올려도 오탐이 늘지 않고 잘려나가던 진짜 매칭만 복구된다.

진짜 제약은 AWS가 아니라 **응답 크기·썸네일 렌더링**:
`search/route.ts:106-111`이 매칭 사진마다 presigned URL을 만든다. 800장 매칭되면
URL 800개 생성 + 브라우저가 썸네일 800장 동시 로딩 → 화면이 버벅인다.
→ **500 정도 + lazy loading / 페이지네이션**이 적정.

> ①을 놓치고 업로드하면 나중에 1만 장 재인덱싱해야 한다. 이게 업로드 전에
> 끝내야 하는 유일한 이유.

## 3. notify-upload 재매칭 — 터질 지점

`api/admin/events/[eventId]/notify-upload/route.ts` (2026-06-08 `040d312`에서 생성,
이후 한 번도 수정된 적 없음)

무슨 기능인가: 참가자가 검색한 뒤에 작가가 사진을 더 올리면, 보관해둔 셀카로
서버가 대신 재검색해서 "회원님이 나온 새 사진 N장" 알림을 보낸다.

문제:
- 참가자 300명분 Rekognition을 **한 요청에서 순차 호출** → 3~5분
  vs 함수 타임아웃 60초(Pro 300초)
- `.catch(() => {})`로 삼켜서 **조용히 실패**. 원인 추적이 어렵다.
- 사람이 많이 검색한 뒤부터 실패하므로 **행사 초반엔 멀쩡하다가 중반에 죽는다.**
- 배치마다 전 범위를 다시 매칭 → 20배치면 300명 × 20 = 6,000회

그런데 결정적으로:
- `search/route.ts:22-39`에 **이미 동일한 재매칭 로직이 있다.**
  마지막 검색 이후 새 사진이 있으면 Rekognition 재호출, 없으면 캐시 반환.
  즉 notify-upload는 이미 있는 기능을 300명분 미리 당겨 돌리는 것뿐.
- **인앱 벨만 있고 웹푸시·이메일·알림톡이 없다.** 두 알림 모두 앱을 열어야 보인다.
  → "앱을 안 연 사람에게 도달한다"는 푸시의 가치가 애초에 없다.
  → 재매칭의 실제 추가 가치는 **셀카 재촬영 1회를 아껴주는 것**뿐.
- 셀카를 S3에 영구 보관하는 **유일한 이유**가 이 기능.
  지우면 얼굴 사진을 검색 시점에만 쓰고 안 남기는 구조가 된다. (개인정보 측면 이득)

선택지 — **삭제** / 병렬화(10~20개씩) / 앱 열 때 지연 재매칭
삭제 시 잃는 것: "회원님이 나온 새 사진 3장" 이라는 **알림의 구체성**,
그리고 셀카 재촬영 1회. "사진이 올라왔어요"보다 후자가 사람을 부르는 힘이 훨씬 세다.
그게 지우면서 치르는 진짜 비용.

## 4. 업로드 알림 중복

작가 5명이 나눠 올리면 **"사진이 올라왔어요"가 20번** 발송 (알림 행 6,000개).
20번 울리는 알림은 무시당한다.

재매칭을 지우면 이게 **유일한 복귀 경로**가 되므로 오히려 더 중요해진다.
→ 재매칭 삭제와 알림 중복 억제는 **반드시 한 묶음**으로. 따로 하면
유일한 복귀 경로가 스팸이 돼서 결과적으로 사진 못 받는 사람이 더 늘어난다.

## 5. 행사를 작가별 5개로 쪼개기 — 권장 안 함

Rekognition이 **단일 공유 컬렉션**(`AWS_REKOGNITION_COLLECTION` 하나)이라
행사를 쪼개도 검색 범위가 안 줄어든다. 행사 구분은 DB 사후 필터링으로만 일어난다
(`search/route.ts:84`).

| | 행사 1개 | 행사 5개 |
|---|---|---|
| 검색 범위 | 1만 장 | **1만 장 (동일)** |
| 셀카 촬영 | 1번 | **5번** |
| 검색 호출 | 300회 | **1,500회** |
| notify-upload 타임아웃 | 300명 루프 | **그대로** |

참가자는 같은 얼굴로 5번 검색해 **같은 결과를 5조각으로** 받는다.
목적이 작가별 관리였다면 `Photo.uploaderId`가 이미 있고 삭제 권한도
업로더 기준으로 나뉘어 있으니(`photos/[eventId]/page.tsx:81`),
**사진관리 화면에 작가 필터 드롭다운** 하나면 부작용 없이 해결.

## 6. 자잘한 것

- **JPEG 전용** (`lib/upload.ts`) — 작가 5명에게 "JPG로 내보내달라" 사전 공지 필요.
  RAW·HEIC로 주면 사전 변환 작업이 생긴다.
- 캐시 조건이 `results.length > 0`(`search/route.ts:38`)이라
  **0장 나온 사람은 새 사진이 없어도 매번 Rekognition 재호출.**
- 인덱싱 API 11,000회의 **실패 재시도 처리**가 있는지 확인 필요.
